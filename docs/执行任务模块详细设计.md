# 执行任务模块详细设计（V1.3.0）

## 1. 目标与本期边界

把测试轮次中的用例转化为可追踪的执行任务，保存每次执行尝试、过程事件、人工介入和最终结果。ChatGPT 可以读取固定的轮次快照，实际执行后通过本地 API 写回步骤事件和结果。

本期完成：整轮/单用例任务建模、任务列表/详情、幂等创建、状态流转、人工/ChatGPT 执行记录、结果登记、取消、人工介入确认、异常中断恢复、事件记录和执行页面。

本期只启用两类受限固定脚本：HTTP 使用只读 DSL；NODE 使用 QuickJS WebAssembly 执行受限 JavaScript 子集。NODE 不运行宿主 Node.js 源码，不暴露 process、require、文件系统、子进程或网络 API，并限制时间、内存和栈。Python、Java/JUnit、浏览器自动化、完整 Node.js 原生 API 和报告生成分阶段实施。

## 2. 领域模型

### 2.1 执行任务

- `EXECUTE_CYCLE`：整轮父任务，`cycle_case_id` 为空；为轮次中的每条用例创建一个子任务。
- `EXECUTE_CASE`：单用例执行任务，`cycle_case_id` 指向轮次用例；整轮父任务的子任务通过 `parent_task_id` 关联。
- 单用例任务也可独立创建，`parent_task_id` 为空。
- 每个子任务关联一条或多条 `dpm_test_execution` 尝试记录；每次重试新增 attempt，不覆盖历史。
- 父任务状态由子任务聚合，不直接执行测试步骤。

### 2.2 执行方式与执行器

| 用例执行方式 | runner_type | 本期处理 |
|---|---|---|
| MANUAL | MANUAL | 用户人工执行并登记结果 |
| AI | CHATGPT | ChatGPT 根据用例/需求/设计快照执行并登记事件和结果 |
| SCRIPT + HTTP | HTTP | 已支持独立只读 HTTP DSL Runner（认证 NONE） |
| SCRIPT + NODE | NODE | 已支持独立 Node Runner；QuickJS WASM 受限 JavaScript 子集，INLINE only |
| SCRIPT + PYTHON | PYTHON | 暂不运行，等待隔离 Runner 阶段 |
| SCRIPT + JAVA | JAVA | 暂不运行，等待隔离 Runner 阶段 |

执行方式和 runner_type 是执行依据，不允许前端自行修改。它们从 `dpm_cycle_case.case_snapshot` 和固定脚本修订读取。

## 3. 状态机

### 3.1 子任务 task_status

- `PENDING`：等待执行器领取或 ChatGPT/用户开始。
- `RUNNING`：正在执行。
- `WAITING_HUMAN`：执行过程等待用户确认/操作。
- `RECOVERY_REQUIRED`：心跳超时或服务中断，需人工确认后恢复。
- `COMPLETED`：执行流程结束；是否通过由 execution.result 决定。
- `FAILED`：执行引擎自身失败，非普通断言失败。
- `CANCELLED`：任务取消。

### 3.2 单次执行 execution_status 与 result

- execution_status：`QUEUED`、`RUNNING`、`WAITING_HUMAN`、`INTERRUPTED`、`COMPLETED`、`CANCELLED`。
- result：`PASS`、`FAIL`、`BLOCKED`、`SKIPPED`；执行未结束时为空。
- `COMPLETED + FAIL` 表示断言失败但执行流程正常结束；`FAILED` task 表示执行引擎异常。
- `dpm_cycle_case.execution_status` 反映最近一次尝试的流程状态；`latest_result` 反映最近一次已完成尝试的结果。

### 3.3 整轮父任务聚合

优先级：任一子任务 RUNNING→RUNNING；否则任一 RECOVERY_REQUIRED→RECOVERY_REQUIRED；否则任一 WAITING_HUMAN→WAITING_HUMAN；全部终态时，任一 FAILED→FAILED，否则任一 CANCELLED→CANCELLED，否则 COMPLETED；其余为 PENDING。

### 3.4 测试轮次自动完成与结果汇总

- 单用例的 `dpm_cycle_case.execution_status` 进入 `COMPLETED` 或 `CANCELLED` 才视为终态；`PENDING`、`RUNNING`、`WAITING_HUMAN`、`RECOVERY_REQUIRED` 均阻止轮次完成。
- 轮次必须至少包含一条用例，且当前状态仍为 `RUNNING`；全部用例进入终态后，自动更新轮次为 `COMPLETED` 并写入 `completed_at`。
- `ABORTED` 不参与自动完成，不能被完成汇总覆盖；空轮次也不自动完成。
- 结果统计从 `dpm_cycle_case.latest_result` 实时聚合：`PASS`、`FAIL`、`BLOCKED`、`SKIPPED`、`NOT_RUN`。取消且未产生结果的用例保留 `NOT_RUN`。
- 不增加统计字段或迁移版本；统计通过列表/详情查询动态计算。
- 完成入口（人工/ChatGPT complete、Runner complete/fail、用户取消、人工介入拒绝）在用例状态更新后调用统一轮次汇总。所有入口先锁轮次，再按父任务、子任务顺序加锁，确保最后两个用例并发结束时只有后一个事务完成轮次。

## 4. 数据库迁移 V1.3.0

复用 V1.0.0 已预留的四张执行表，不重建、不清空历史数据。

### 4.1 dpm_execution_task

- `parent_task_id`：整轮父任务与单用例子任务关系。
- `idempotency_key`：同一轮次下创建请求幂等键，唯一约束 `(cycle_id,idempotency_key)`；子任务为空。
- `lease_owner`、`lease_token_hash`、`lease_expires_at`：为独立 Runner 的领取租约预留；数据库不保存明文 Runner Token。
- `cancel_requested_at`：为异步 Runner 协作取消预留。
- 索引：父任务状态索引、任务领取索引、轮次幂等唯一索引。

### 4.2 dpm_test_execution

- `checkpoint_json`：保存步骤级检查点，服务/Runner 中断后供 ChatGPT 判断从哪里恢复。
- 原有 `(cycle_case_id,attempt_no)` 唯一约束继续保证同一用例的尝试号不重复。

### 4.3 dpm_execution_event

- `event_key`：调用方生成的事件幂等键；同一 execution 的同一 event_key 只能写入一次。
- 执行快照、事件 JSON 和文本日志递归脱敏 password、token、cookie、authorization、secret、apiKey、privateKey、credential 等字段及常见键值对；事件幂等键不允许承载秘密信息。

## 5. 任务创建规则

1. 只能对状态为 RUNNING 的测试轮次创建执行任务；PLANNED 轮次必须先开始。
2. 整轮任务创建一个父任务，并为每条 `dpm_cycle_case` 创建一个子任务及首个 QUEUED execution。
3. 单用例任务必须校验 `cycle_case_id` 确实属于 URL 中的 `cycle_id`。
4. 同一用例不能同时存在 PENDING、RUNNING、WAITING_HUMAN 或 RECOVERY_REQUIRED 任务；整轮任务与单用例任务互斥检查。
5. 创建任务时锁定轮次行和目标轮次用例行，按该用例历史最大 attempt_no + 1 生成新尝试。
6. 同一轮次内重复提交相同 Idempotency-Key，返回已有任务，不重复创建执行记录。
7. 执行状态变更统一按「测试轮次 -> 父任务 -> 子任务 -> 执行记录」加锁，再读取子任务聚合状态；轮次行锁串行化同一轮次的并发用例完成，避免父任务汇总和轮次完成判断出现竞态。
8. PROD 环境本期不允许自动执行；只允许 MANUAL 方式建立任务并由人工登记结果。
9. 创建执行记录时保存预期结果和环境/代码基线的非敏感快照；凭据只保存 credential_ref，不复制秘密。

## 6. API 设计

统一前缀：`/api`。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/test-cycles/{cycleId}/execution-tasks` | 创建整轮任务；Idempotency-Key 必填或由客户端生成 |
| POST | `/api/test-cycles/{cycleId}/cycle-cases/{cycleCaseId}/execution-tasks` | 创建单用例任务 |
| GET | `/api/execution-tasks` | 分页查询父任务/独立任务 |
| GET | `/api/execution-tasks/{id}` | 任务详情、子任务、attempt、事件 |
| GET | `/api/execution-tasks/claimable/chatgpt?limit=10` | 查询待 ChatGPT 执行的 AI 用例及不可变快照；仅发现候选，不锁定任务 |
| POST | `/api/execution-tasks/{id}/cancel` | 取消父任务或单用例任务 |
| POST | `/api/execution-tasks/{id}/resume` | 从 RECOVERY_REQUIRED 显式恢复，创建新 attempt |
| POST | `/api/execution-tasks/{id}/human-intervention` | 确认或拒绝人工介入 |
| POST | `/api/execution-tasks/{id}/executions/{executionId}/start` | ChatGPT/人工开始单次执行 |
| POST | `/api/execution-tasks/{id}/executions/{executionId}/events` | 写入步骤、断言、日志、检查点事件 |
| POST | `/api/execution-tasks/{id}/executions/{executionId}/complete` | 登记 PASS/FAIL/BLOCKED/SKIPPED 及实际结果 |
| POST | `/api/runner/claim` | 独立 Runner 使用共享 Token 领取 HTTP/NODE 任务；runnerType 默认 HTTP 兼容旧客户端 |
| POST | `/api/runner/tasks/{taskId}/heartbeat` | Runner 续租 |
| POST | `/api/runner/tasks/{taskId}/events` | Runner 上报请求、响应和断言事件 |
| POST | `/api/runner/tasks/{taskId}/complete` | Runner 提交执行结果 |
| POST | `/api/runner/tasks/{taskId}/fail` | Runner 报告引擎异常 |

执行详情接口始终以 task_id + execution_id 联合校验，不能跨任务写入其他执行记录。

## 7. ChatGPT 参与执行的协议

1. ChatGPT 调用 `GET /api/execution-tasks/claimable/chatgpt?limit=10` 获取待执行 AI 用例。该接口只发现候选，不锁定任务；只返回 RUNNING 轮次、非 PROD 环境、PENDING 任务和 QUEUED/CHATGPT/AI 执行记录。
2. 读取返回的 `task` 和 `execution`。`execution.requestSnapshot` 包含用例步骤、预期结果、`aiInstruction`、测试数据、环境快照及代码版本；不包含明文凭据。
3. 调用 `POST /api/execution-tasks/{id}/executions/{executionId}/start`，请求 `actor=CHATGPT`。服务端通过轮次、父任务、子任务的固定顺序行锁和状态条件完成原子认领；并发重复认领只有一个成功。
4. ChatGPT 根据 `aiInstruction` 和用例步骤动态制定执行逻辑。每个关键步骤调用 events，记录 STEP_STARTED、STEP_COMPLETED、ASSERTION_PASSED/FAILED、API_REQUEST/API_RESPONSE、LOG；阶段性调用 CHECKPOINT 保存当前进度并刷新心跳。
5. 遇到登录、验证码、授权、付款、删除、发布或其他需要人工确认/不可自动完成的动作，调用 WAITING_HUMAN 事件并暂停，不绕过安全控制。用户通过 human-intervention 确认后，任务回到 PENDING/QUEUED；ChatGPT 重新获取队列、读取最新检查点并继续同一 attempt。
6. 所有步骤完成后调用 complete，提交 PASS/FAIL/BLOCKED/SKIPPED、实际结果摘要和日志。断言失败是测试结论 FAIL，不等同于执行引擎 FAILED。
7. 若 ChatGPT 会话或 Runner 异常中断，超时扫描转入 RECOVERY_REQUIRED；用户显式恢复后创建新 attempt 并继承 checkpoint，ChatGPT 从检查点继续，不自动重放可能产生副作用的步骤。

## 8. 中断恢复

- RUNNING 任务通过 heartbeat_at/event 更新心跳；心跳超过 5 分钟未更新后，由每 60 秒运行一次的恢复扫描器将任务置为 RECOVERY_REQUIRED，当前 attempt 标为 INTERRUPTED，并追加 EXECUTION_INTERRUPTED 事件。
- 扫描器先查询候选任务，再按「轮次 -> 父任务 -> 子任务」加锁；最终通过带有 heartbeat_at 过期条件的 UPDATE 原子抢占任务。若 Runner 在候选查询后刷新心跳，UPDATE 返回 0，执行记录保持 RUNNING。
- 抢占任务成功后才更新 execution 为 INTERRUPTED；若执行记录更新失败，抛出运行时异常回滚整个事务，禁止只提交任务状态。
- 恢复必须由用户显式触发；不自动重放可能产生副作用的步骤。
- 恢复时保留旧 attempt，新增 attempt_no=max+1；checkpoint 作为恢复参考而不是保证自动重放。
- 取消与完成采用「轮次 -> 父任务 -> 子任务 -> 执行记录」锁顺序及状态条件更新；取消只终止当前最新 attempt，保留历史 attempt；取消后拒绝迟到的结果回写。
- 测试轮次终止先锁定轮次行并将状态更新为 ABORTED，再按「轮次 -> 父任务 -> 子任务 -> 最新 execution」顺序取消活动任务。PENDING、RUNNING、WAITING_HUMAN、RECOVERY_REQUIRED 均转为 CANCELLED，并清空 Runner lease；已完成子任务和历史 attempt 保持不变。
- MANUAL/CHATGPT 开始和 HTTP/NODE Runner 领取任务时，先锁定轮次并确认 RUNNING；Runner 心跳/事件/完成以及 ChatGPT/人工状态变更均先锁轮次，再锁父子任务，并与轮次终止串行。轮次终止后，迟到的 start、heartbeat、complete 请求必须被拒绝。

## 9. 安全边界

- Web 服务仍只监听 127.0.0.1:18090；Runner 不监听入站端口，后续通过本机 HTTP 轮询。
- 不在 Spring Boot 进程中执行脚本源码，不使用 ProcessBuilder 启动用户源码。HTTP DSL 和 NODE QuickJS WASM 受限 JavaScript 子集是当前仅有的自动化脚本执行方式。
- HTTP Runner 已独立运行于 Node.js 进程，通过本机 HTTP 轮询，不开放入站端口；只读方法、目标主机绑定环境快照、禁止重定向跟随、响应体限制 100 KiB。
- NODE Runner 宿主进程独立于 Spring Boot；用户源码只在 QuickJS WASM guest heap 中执行，不向 guest 暴露宿主 Node.js、文件、子进程或网络能力；执行限制 5 秒、32 MiB guest heap、512 KiB 栈、100 KiB 源码、256 KiB 输入、最多 100 条断言。此能力是受限 JavaScript 子集，不是完整 Node.js 运行时。
- PYTHON/JAVA 通用脚本 Runner 后续仍需先确定操作系统级隔离或等效安全边界；FILE 路径先 canonicalize 并确认仍在脚本根目录内。
- HTTP Runner 仅允许配置的目标主机、默认只读方法；禁止 SSRF、内网任意探测和生产写操作。
- PROD 自动化写操作默认禁止；需要明确的环境策略和逐次人工审批。
- Runner 认证使用本机私有配置中的随机 Token，服务端只存 Token 哈希并做常量时间比较；不记录 Token。

## 10. 验收标准

1. 整轮任务可生成父任务和 N 个子任务；单用例任务只生成一个执行子任务。
2. 同一 Idempotency-Key 重复请求不重复建任务或 execution。
3. 同一 cycle_case 并发创建任务只能成功一个；跨轮次 cycle_case ID 被拒绝。
4. MANUAL/CHATGPT 可以开始、记录事件和完成；断言 FAIL 不等同于引擎 FAILED。
5. 取消后迟到的完成回写被拒绝；父任务状态正确聚合。
6. WAITING_HUMAN 可确认后继续；中断恢复保留旧 attempt 并生成新 attempt。
7. PROD 自动执行被拒绝；密码、Token、Cookie 等敏感内容不能写入事件。
8. Maven 构建、API 冒烟和数据库迁移验证通过；不影响已有 18 张表数据。
