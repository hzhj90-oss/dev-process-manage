日期：2026-11-12；代码根目录：D:\code\dev-process-manager。

## 背景和实际发现

从项目创建、版本规划、需求、详细设计、测试用例、轮次执行到报告的功能模块已基本具备，但用户在「需求与详细设计」列表中只能看到**关联用例的计数**，无法直接查看这条需求关联的测试用例。跨模块追踪需要跳转到用例列表并人工搜索；搜索用例编号/标题又不等于精确关联，在多需求覆盖的真实场景可能漏报或误报。本批优先补这一条真实操作阻塞，而不是增加非必要模块。

前期的真正写入型全链路验收脚本 scripts/test-business-flow-real-db.mjs 早已有专门的 DPM-VERIFY-FLOW- 测试项目记录。为了不污染工作区和既有数据库，**本批没有再次运行写入型端到端脚本**。采用既有标记项目的 GET-only 复核与真实 Chrome 页面点击，把关键链路完整跑通。

## 业务功能开发

### 需求 → 关联测试用例

- frontend/src/views/RequirementListView.vue：把原本只展示数字的「关联用例」列调整为可点击的「N 条」。当数量为 0 时不可点击。点击某需求时打开测试用例页并携带唯一需求 ID；不会写数据库。
- frontend/src/utils/contextNavigation.js：为 test-cases/requirementId 增加严格白名单路由。只允许单个、无前导零、无正负号、非科学记数法、正整数 ID；不能通过格式不规范的 query 数组/对象和不匹配的路由组合生成链接。
- frontend/src/views/TestCaseListView.vue：路由上下文 requirementId 非空且规范时，在列表顶部明确提示“正在查看需求 #ID 关联的测试用例”，查询使用独立的 requirementId 过滤参数而不是模糊 keyword；支持“返回全部用例”，路由 query 改变后正确重新分页查询；非法 query 按未筛选状态处理。原状态、类型、优先级、执行方式和关键字筛选可继续与需求关联条件 AND 组合。
- backend TestCaseController：GET /api/test-cases 增加可选 requirementId Long，保留全部原有过滤参数。
- backend TestCaseService：校验 requirementId 必须正数，保持旧 page(...) 方法签名用于内部调用兼容；新重载方法将 requirementId 传入 mapper 的分页 SQL 与 count SQL。
- backend TestCaseMapper.java 与 mapper/testcase/TestCaseMapper.xml：使用 EXISTS (SELECT 1 FROM dpm_requirement_case WHERE test_case_id = c.id AND requirement_id = :requirementId)，避免 JOIN 给每个用例引入重复行，并保证 count 和实际分页条件一致。**不新增表，不执行 DDL。**
