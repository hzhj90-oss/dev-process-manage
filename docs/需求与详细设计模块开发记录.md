# 需求与详细设计模块（第二阶段）

## 1. 实现范围

本阶段复用 V1.0.0 已有的 dpm_requirement、dpm_requirement_design 两张表，不新增 DDL、不调整已有字段。
一个版本包含多条需求；一条需求可以保存多个详细设计修订版本。

## 2. 需求管理

页面：/#/requirements

API：
- GET /api/requirements：分页查询。
- GET /api/requirements/{id}：需求详情。
- POST /api/requirements：新增需求。
- PUT /api/requirements/{id}：编辑需求。

查询条件：
- versionId：按版本过滤。
- keyword：匹配需求编号、标题、项目编码、版本号。
- status：需求状态。
- priority：优先级。

需求字段：
- versionId：所属版本，必填；创建后不可变更。
- requirementNo：需求编号，在同一版本内唯一。
- title：需求标题，必填。
- requirementType：需求类型。
- contentMarkdown：需求描述，使用 Markdown 保存。
- status：DRAFT、CONFIRMED、DEVELOPING、COMPLETED、CANCELLED。
- priority：LOW、MEDIUM、HIGH、URGENT。
- ownerName：负责人。
- sortOrder：列表排序值。

新增和编辑时校验所属版本存在且未归档；不提供物理删除，避免历史测试关联失效。
列表展示所属项目/版本、设计修订数、关联用例数和最新设计修订号。

## 3. 详细设计修订

API：
- GET /api/requirements/{id}/designs：按修订号倒序查询。
- GET /api/requirements/{id}/designs/{designId}：读取指定修订。
- POST /api/requirements/{id}/designs：新增一个设计修订。

设计字段：
- revisionNo：由后端按需求自动递增，从 1 开始。
- designType：GENERAL、API、DATABASE、CODE、UI、TEST 等类型标识。
- title：设计标题，必填。
- contentMarkdown：设计内容，必填。
- attachmentPath：可选附件相对路径。
- status：DRAFT、IN_REVIEW、APPROVED、REJECTED、SUPERSEDED。
- authorName：作者。

设计修订采用追加模式：不提供覆盖更新和删除接口；保存新版本不会修改旧版本。
创建修订时对需求主记录加行锁，再计算 MAX(revision_no)+1，避免并发提交产生相同修订号。
所属版本已归档时，不允许新增设计修订。

## 4. 前端交互

- 需求列表支持版本、关键词、状态、优先级筛选及分页。
- 新增/编辑需求使用表单弹窗。
- 编辑时所属版本锁定，避免需求在版本之间迁移。
- 点击设计版本数或“设计”进入修订历史。
- 左侧选择历史修订，右侧查看 Markdown 原文。
- “新增修订”打开编辑弹窗，保存后生成新版本并自动选中。
- 当前页面以 Markdown 原文预览，不引入额外 Markdown 渲染依赖。

## 5. 数据库与接口验证

不新增迁移脚本；复用：
- dpm_requirement：需求主数据。
- dpm_requirement_design：详细设计修订历史。
- dpm_requirement_case：需求与测试用例关联统计（本阶段只读统计）。

验证内容：
1. 新增项目、版本和需求。
2. 需求更新后读取到最新标题、状态和优先级。
3. 同一版本重复需求编号返回 HTTP 409。
4. 同一需求连续创建两个设计修订，返回修订号 1、2。
5. 设计历史按修订号倒序返回，旧版本内容保留。
6. 需求详情设计数为 2，版本详情需求数为 1。
7. 按 versionId + keyword 过滤需求正确。
8. 前端静态入口 HTTP 200。
9. 本阶段首次验证数据当时已清理；后续测试轮次快照联调创建并保留了本地项目/版本/需求/用例验证数据（项目 id=4、版本 id=4、需求 id=2），编号前缀为 `DPM-VERIFY-20261108`，仅用于本地快照验证。

## 6. 后续进展与当前未实现

后续第三阶段已完成测试用例维护和需求-用例多对多关联编辑；测试轮次创建时会固定需求正文、覆盖类型和最新详细设计修订，后续需求/设计修改不会改变已保存的轮次快照。
