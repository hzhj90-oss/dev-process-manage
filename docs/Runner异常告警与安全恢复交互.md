# Runner 异常告警与安全恢复交互

日期：2026-11-11

## 当前能力

原有服务已具备租约心跳与定时超时恢复，`ExecutionRecoveryScheduler` 每分钟扫描一次失联任务；超过到期条件时标记 `RECOVERY_REQUIRED`，不会自动重放脚本。

本轮完善的是用户能够及时看见异常、定位任务并安全决定是否恢复。

- 执行任务页新增「待处理事项」卡片：待执行、待人工处理、待恢复三个计数，每 30 秒从原有分页接口读取总量。
- 点击「查看任务」自动筛选对应状态，不需要手动输入任务编号。
- 存在待恢复任务时显示警告，提示检查旧执行结果和业务副作用；等待人工任务也有对应提醒。
- 结合上一轮 Runner 在线监控，对已经观察过但超过 30 秒没有联系的 Runner 显示离线告警。
- 在单用例任务列表提供「人工恢复」入口，任务详情和原有操作仍可使用。

## 人工恢复保护

恢复按钮不直接发起重试，而是重新读取最新任务详情，要求类型为 `EXECUTE_CASE`、状态为 `RECOVERY_REQUIRED` 且最后一次执行为 `INTERRUPTED`。

恢复前弹出需要**手动输入「恢复」**的二次确认。HTTP/Node/Browser 固定脚本明确提示将重新从第一步执行，必须先核实上次操作不会产生不可重复的业务副作用；其它类型则要求核对历史日志和检查点。

取消、输入错误或状态已变更时，前端不调用 `POST /api/execution-tasks/{id}/resume`；后端原有事务、状态检查与租约锁继续作为最终约束。

本轮没有实现自动重试、没有绕过人工确认，也没有新增数据库表或修改恢复调度器。

## 验证策略

`runner/browser-runner/browser-attention-smoke.mjs` 使用真实 Chrome 运行，但把「2 待恢复、1 待人工、5 待执行」及离线 Runner 场景模拟在浏览器网络层，不写入真实任务。

覆盖告警显示、一键状态筛选、专用模拟单用例的恢复按钮、确认框重复操作提示、错误输入提示和取消操作；监控恢复 API 调用次数必须为 0。

该测试已加入 `scripts/test-browser-integration.ps1` 的可选本地浏览器集成回归。

## 使用与边界

打开：`http://127.0.0.1:18090/#/execution-tasks`。

当前待恢复计数为 0 是正常情况；测试场景中的 2 个待恢复任务仅为浏览器模拟数据。不能为了 UI 演示停止正在执行的 Runner 或人为篡改历史任务状态。

待恢复状态不会自动再次执行；需要操作者核实上一次执行的外部系统影响，再手动完成确认。用户未要求提交，本轮所有变更保留在本地 Git 工作区，未 commit/push。

### 额外验证：有效确认路径

同一个真实 Chrome 模拟测试还验证了输入正确的「恢复」后恰好发起一次恢复 API 调用，返回由浏览器路由模拟的 HTTP 200；实际数据库没有写入。本测试同时验证输入错误和取消时调用 0 次，最终输出：`BROWSER_ATTENTION_UI_PASS counters=5/1/2 alerts=3 recovery-posts=1-after-confirmation`。
