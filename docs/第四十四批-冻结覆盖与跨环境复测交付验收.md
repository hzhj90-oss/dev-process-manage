## 为什么做本批

第43批补齐“需求→用例→加入正确版本计划轮次”操作，确保后端在轮次快照中只保存同版关联需求。但用户在轮次详情中仍需逐条展开用例查看需求编号、详细设计和结果，无法直接判断本轮覆盖多少个**不同需求**、通用回归用例有多少、快照缺失设计有多少。尤其在跨版本加入通用用例时，“本轮用例 N 条”不能视为“覆盖 N 个需求”。

同时第41批的跨轮次结果对比已有修复、回归、新增/移出等分类，但没有显示两轮的环境标识和代码版本差异。相同用例即便 FAIL→PASS，也可能是环境或版本变化。为了避免分析误导，需要将变更上下文显式呈现。

## 开发项目一：轮次详情冻结需求覆盖汇总

- frontend/src/utils/cycleCoverage.js 读取 GET /api/test-cycles/{id} 已有冻结 cases[*].requirements、designSnapshotJson 和 latestResult；不读取实时需求/设计，不增加后端查询或数据库DDL。
- 按稳定 requirementId 去重，显示：需求数、关联需求用例数、无需求通用用例数、缺设计快照的**用例-需求关联数**（不是缺设计需求数）。一条用例覆盖多个需求、多个用例覆盖同一需求时不会误把关联条数当需求数。
- 逐需求表格显示用例数、PASS数、FAIL/BLOCKED数、NOT_RUN/SKIPPED数，以及有多少关联缺设计快照。缺失或坏 JSON 不冒充已具备设计；完整历史设计以冻结版本为准。
- 遇到重复的轮次用例快照、同用例重复需求ID、缺失需求编号/ID或不完整响应时，界面显示“无法核对”，拒绝给出看似正确的统计数字；不阻断原轮次详情显示。
- TestCycleListView.vue 在轮次环境/代码信息与用例表之间显示覆盖汇总表、提示和警告；移动端降为2列。仍保留逐用例展开查看需求、设计和执行步骤。
- 新增 frontend/src/utils/cycleCoverage.test.mjs 共5项：跨用例需求去重、通用用例统计、设计部分缺失、无效/重复快照拒绝、坏设计JSON不误判。已加入 scripts/verify-local.ps1。

## 开发项目二：轮次对比显示可比性

- backend TestReportService.compare 只读扩展上一已完成轮和当前轮的 environmentId、environmentName、codeVersion、gitCommit，并返回 environmentChanged、codeVersionChanged。未有上轮或关键ID/代码版本缺失时返回null，不能把未知误报为“环境一致”。代码版本变化或双方有完整Commit且Commit变化时明确标识。
- 返回只包含环境名称/ID和代码版本/Commit，不返回环境凭据、连接地址、配置快照等敏感材料；仍保持只读GET、no-store、nosniff。
- 前端 TestReportListView.vue 的“轮次对比”顶部显示**上一轮环境/版本 → 本轮环境/版本**；环境不同、代码不同或记录不足会分别提示，保留原有“失败转通过”“新增回归失败”“范围变更”列表。仅是结果变化，不能证明缺陷根因。
- 前端 roundComparison.js 新增 comparisonContextWarnings；既有 roundComparison.test.mjs 补第6项测试，覆盖环境/代码变化、缺失字段、完全一致、首轮无基准。
- Java TestReportCompareServiceTest 补2项测试：不同环境/构建能正确报告且不泄露环境快照；缺失信息为未知、双方相同为false。没有修改旧数据、DDL或任务状态。
