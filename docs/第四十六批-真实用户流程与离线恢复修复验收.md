## 一、修复离线回滚任务数错误判断

复核 `scripts/rollback-release.ps1` 发现：`-AllowOffline` 在应用完全停止后把活跃任务数设为 `UNKNOWN_OFFLINE`，但原共享的 `if ($active -ne 0)` 依旧执行，导致**合法的离线程序包恢复永远被拒绝**。这是实际控制流错误，之前11项隔离测试没有覆盖“已停服务且任务API不可用”的分支。

现在把判定统一到 `scripts/release-common.ps1` 的 `Assert-DpmRollbackTaskGuard`：
- **在线模式**必须收到有效非负数字0；任务数1/未知/非法都拒绝；
- **离线模式**仅允许明确的 `UNKNOWN_OFFLINE` 标记，前提仍是`-AllowOffline`路径在前后两次检查中都证明端口未监听且目标Java进程不存在；
- 两种模式都保持完整快照SHA校验、指定精确快照、`-Apply`以及环境变量双重授权；没有弱化安全检查，更没有自动执行任何真实回滚。

`scripts/test-release-safety.ps1` 从11项增加到**18项**：离线标记通过、在线0通过、在线有任务/未知/非法/负数拒绝、离线标记不合法拒绝，连同原有路径逃逸、篡改、完整性及交换恢复隔离测试。最终 `RELEASE_SAFETY_PASS cases=18 actualRollback=false backendWrites=0`。

**限制：**这证明逻辑判断和临时目录中的恢复流程可行，尚不能代表在真正停止的业务服务上已成功演练。第46批没有执行真实`-Apply`，没有操作原数据库或任务。

`frontend/src/views/TestCycleListView.vue` 修复：
- 首次通过`?caseId`进入：等页面版本/环境/用例选项完整加载后，**自动打开来源用例加入向导**；GET再次读取当前用例、需求关联版本和PLANNED轮次，拒绝错版/失效用例。

旧 `browser-case-cycle-placement-smoke.mjs` 真实Chrome改成直接等待弹窗，而不是再次点“选择目标轮次”，同时核对计划轮次过滤、无需求通用用例跨版本警示、新建轮次自动预选、目标轮次已开始拒绝并且不重复POST。最终 `BROWSER_CASE_CYCLE_PLACEMENT_PASS ... backendWrites=0`。
