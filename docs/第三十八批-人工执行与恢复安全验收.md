# 第三十八批：人工执行、结果登记、人工介入与恢复安全验收

日期：2026-11-12；项目 D:\code\dev-process-manager；继续第三十七批断点。

## 本批重点

对执行任务页中有副作用、需要人工参与的 4 条核心链路进行一次完整加固：
1. 人工或 ChatGPT 执行开始；
2. 人工执行结果登记；
3. 等待人工确认时的「确认继续」或「拒绝」；
4. RECOVERY_REQUIRED 状态下的人工恢复。

此前页面在发起异步请求之前没有统一的操作锁，连续双击可能重复弹框/重复 POST；弹窗期间任务状态可能被 Runner 或其他窗口改变；结果保存成功但响应失败时，旧表单容易被继续提交；任务恢复需要人工核实中断风险而不能自动执行。

## 代码变更

frontend/src/views/ExecutionTaskListView.vue：

- 新增全局任务操作临界区 taskAction（shallowRef）。在任何异步校验或人工确认框前立即登记 type/taskId/executionId，保证执行开始、结果登记、人工介入、任务恢复和上一批的取消任务操作互相排斥。
- 所有列表/子任务/详情相关入口和嵌套的 ExecutionAttempts 动作按钮，在有操作进行时 disabled，并在对应请求期间显示 loading。所有临界区期间禁止关闭详情弹窗；结果提交时禁用关闭按钮、表单与取消，避免误关闭或修改正在提交的结果。
- 开始执行前重新 GET task，严格要求 EXECUTE_CASE/PENDING + 精确 executionId/QUEUED/对应 MANUAL 或 CHATGPT；不可人工触发固定 Runner 执行。
- 结果提交前复制固定 taskId/executionId/表单内容，重新 GET 校验 RUNNING 的 MANUAL attempt，执行结果只接受 PASS/FAIL/BLOCKED/SKIPPED。POST 后校验返回的任务 ID 与 COMPLETED 状态。
- 网络失败不自动再次执行。结果登记 POST 超时后再次读取任务：若已经不在 RUNNING 或执行尝试状态发生变化，关闭提交弹窗，阻止人为再次登记同一结果；否则保留用户原输入供检查后手动重试。
- 人工确认或拒绝：获取人工输入后再 GET，确认任务依然 WAITING_HUMAN 且最新 execution 同样 WAITING_HUMAN，才 POST；检查 CONFIRMED -> PENDING 或 REJECTED -> COMPLETED 的目标响应。
- 恢复任务：首次 GET 确认确实 RECOVERY_REQUIRED + 最新 attempt INTERRUPTED，固定原 attempt ID，向用户显示固定脚本重新从头执行等风险提示，要求输入「恢复」。提交前二次 GET 对比任务状态和原 attempt ID，变化则拦截，不创建第二条恢复尝试；成功验证返回 PENDING。
- 所有修改无论正常还是错误后均重新读取当前任务详情、任务列表和待处理统计；不改变数据库结构、不自动运行危险测试。
- 修复了实际 Chrome 首轮验收发现的状态锁释放错误：普通 ref 会将对象代理，导致用引用相等判断释放时为假；改用 shallowRef 保留 token 引用身份，按钮在完成后正常恢复。
- 取消任务继续维持第36批的确认与服务端状态重新校验，并纳入 taskAction 联合锁，防止不同操作相互冲突。
