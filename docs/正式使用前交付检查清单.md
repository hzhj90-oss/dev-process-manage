# 开发管理系统正式使用前交付检查清单

版本：第47批本机交付审查（2026-11-12）；Windows T14s；项目根目录：D:\code\dev-process-manager。

## 0. 当前范围

本系统面向**受控本机使用**。已经具备项目、版本、需求、详细设计、用例、测试轮次、执行任务、结果报告、证据附件、复测对比、Runner、备份和守护。没有登录/权限验证，不应暴露公网。当前只运行 HTTP、Node、Browser Runner；Docker、Python/Java Runner、自动无人值守 ChatGPT 队列不在本次交付范围。

**验收通过不等于生产级安全批准。** 在未设计鉴权/网络隔离之前，只按本地端口使用；用户明确取消了登录功能，这一限制必须明确告知后续使用者。

## 1. 开始工作的10个检查点

- [ ] **入口和进程**：访问 http://127.0.0.1:18090 ，页面没有错误。用 scripts/service-status.ps1 核对 Java 应用与 HTTP/Node/Browser Runner 各1实例，health=UP。
- [ ] **活动任务**：GET /api/execution-tasks?status=RUNNING&pageNum=1&pageSize=1；若有进行中的任务，暂停部署或停服，避免中断实际执行尝试。
- [ ] **Windows窗口**：守护/备份任务显示 WINDOWLESS_LAUNCH=True；启动、停止和定时任务不能闪 CMD/PowerShell，避免影响电脑日常操作。
- [ ] **项目和版本**：从首页→项目→查看版本→需求，确认项目/版本筛选准确；多个需求可以属于同一版本。
- [ ] **需求与设计**：录入需求并添加详细设计修订；修订不能覆盖原设计历史。关键字段需要完整。
- [ ] **用例覆盖**：在需求页点击新增用例，确认默认预选来源需求及所属版本。测试步骤、步骤预期、整体预期结果齐全。
- [ ] **轮次归属**：从用例页加入轮次时，已关联需求的用例只显示同版本 PLANNED 轮次；通用用例可跨版本，但不自动形成需求覆盖快照。
- [ ] **环境与构建**：测试轮次必须填写环境和实际代码版本；Git commit 建议填写可追溯 SHA。环境改变/代码版本改变时，复测报告应有差异提示。
- [ ] **测试与证据**：检查轮次启动、单例或整轮执行任务是否真实领取、结果是否及时回写；证据附件是否归属本次 attempt，网络异常不能无条件重复 POST。
- [ ] **报告与诊断**：轮次详情展示冻结需求覆盖总览，未关联需求用例单独计数；报告可查看与导出、轮次对比能区分修复/回归失败/范围变化；历史22条状态异常只读诊断，不得在日常使用中批量修复。

## 2. 日常操作口径

需求覆盖数是**本轮快照中不同需求ID的数量**，不是“版本全部需求已经覆盖”；一条用例覆盖多个需求、多条用例覆盖同一需求时，界面避免重复计数。无需求的通用用例单独列示，不能简单把用例总数当做覆盖率。

测试轮次快照中的需求及设计**不随当前版本的编辑自动更新**。新增版本/新一轮测试要重新冻结；已有已完成轮次不可直接增删用例。轮次详情的设计缺失计数表示“冻结时没有设计快照”，不代表实时需求没有设计。异常快照会显示不可核验错误，不会给出假统计。

轮次对比限**同一版本、上一已完成轮次**，按原始 testCaseId 匹配。即使看到 FAIL→PASS，也应先确认环境、代码版本、Commit、用例修订是否可比，不能直接认定是缺陷修复。

## 3. 服务、备份和恢复准备

- [ ] **服务状态**：在项目目录运行 scripts/service-status.ps1 查看守护计划任务、服务和Runner。上次结果为 0 表示任务完成；正在执行时 Windows LastTaskResult 可能暂时显示非零运行状态，需在任务 Ready 后核对。
- [ ] **最新备份**：scripts/backup-status.ps1 -Verify 检查备份新鲜度、manifest、SQL GZip 与附件 ZIP 的 SHA-256 和完整性。备份由自动计划任务每天本机时间 02:30 执行，电脑关机或未登录时可能延迟；48小时之外为过期。
- [ ] **只读还原预检**：scripts/test-database-isolated-restore.ps1 默认不写入，验证备份结构和严格操作保护。
- [ ] **隔离还原演练**：只有明确批准时，设置 DPM_ISOLATED_RESTORE_ALLOW_WRITE=YES 并用 -Apply 对备份启动独立临时 MySQL 5.7 随机本地端口。参考 docs/数据库隔离还原验收.md。**绝不还原到运行中的业务库 127.0.0.1:3306**。
- [ ] **异机容灾**：备份与MySQL在同一电脑，硬盘损坏会同时损失两者。正式依赖这些数据前，应规划安全加密的离线/异机副本，并做恢复演练；不要将SQL/凭据/附件提交Git。
- [ ] **日志与敏感信息**：查看 logs/ 与 .local/ 下文件的访问权限，确保凭据不在开发文档、Git或审计输出中。数据库原理和凭据存储参考 docs/数据库自动备份与恢复验证.md。

## 3.1 程序版本发布及回滚（第45批）

- [ ] **发布前预检**：运行 `scripts/check-release-readiness.ps1`，确认单实例、端口仅监听本机、RUNNING任务0、最新数据库/附件备份有效，且存在已校验的JAR快照。累计未提交Git修改仅作为风险显示；`-Strict`才要求清洁工作区。
- [ ] **程序包快照**：使用 `scripts/create-release-snapshot.ps1 -DryRun` 检查后再执行同脚本创建快照。保存在受访问权限保护的 `data/release-snapshots`，包括JAR、清单和SHA256；与MySQL数据库/附件备份相互独立。
- [ ] **回滚只读预览**：执行 `scripts/rollback-release.ps1`，核对目标快照名称、SHA256和运行中任务数。默认不改变服务；`-Apply`必须同时提供准确名称、完整哈希和 `DPM_RELEASE_ROLLBACK_APPROVE=YES`。
- [ ] **后端已停的恢复**：如果编译或启动失败导致应用已完全停止，可按 `docs/第四十五批-本地发布快照与回滚保护验收.md` 使用显式 `-AllowOffline`；严格检查端口/进程都空闲。该模式仍需人工批准，**本批没有进行真实停服恢复演练**。
- [ ] **失败保护**：只允许按固定路径从校验快照换回JAR，不做任何数据库回滚或任务自动重试；恢复失败应保持watchdog暂停，停止继续自动操作。
- [ ] **离线验证**：`scripts/test-release-safety.ps1` 在临时目录完成18项隔离安全校验和文件交换/恢复测试；不会真实停服。正常全量回归可显式加 `-ReleaseSafety` 一并执行。新版本JAR与旧数据库结构兼容性仍需单独确认。

## 3.2 源码交付审计（第47批）

- [ ] **全部源码文件清点**：运行 `node scripts/audit-release-worktree.mjs`；同时检查 Git 已跟踪和未跟踪文件，不把 `git diff --check` 当作对未跟踪源码的完整检查。发现凭据特征、软链接、异常二进制、运行数据、冲突标记、未隐藏的嵌套 PowerShell 时必须人工排查；审计不打印文件正文和凭据值。
- [ ] **严格发布门槛**：运行 `node scripts/audit-release-worktree.mjs --strict`；本地尚有未提交改动时故意返回非零。普通版本 `check-release-readiness.ps1` 可以在开发工作区通过本机运行检查，**不等于源码已同步或通过远端 CI**。
- [ ] **发布身份**：整理并逐项审核现有源码差异，用户明确要求后才进行分组 commit/push；随后核对 GitHub Actions 当前版本的结果及构建产物哈希，不能把旧的成功记录认作新代码通过。
- [ ] **运行版本可恢复**：发布检查现强制确认当前运行中的 JAR 存在 SHA-256 完全一致的已验证快照；这只覆盖 JAR 二进制，不能倒退 MySQL DDL 或附件。
- [ ] **保密与机器依赖**：`.local`、`data`、`logs` 和 `node_modules` 继续保持忽略；所有凭据本机保留；同机备份不是异机容灾，正式长期依赖前需要用户选定安全的外部加密备份目标。

## 4. 推荐验收脚本（不写真实业务记录）

下列脚本在已经安装本地环境的前提下运行。为避免 Windows 页面文件不足，**不要并行运行两组 Chrome**。启动测试命令应采用隐藏窗口方式，避免影响使用电脑。

1. scripts/verify-local.ps1 -AuditDependencies -IncludeMySql -BrowserIntegration：标准综合回归，包含 MySQL 隔离集成、后端测试、前端与浏览器、Runner、安全审计；浏览器 POST/PUT/DELETE 在模拟层拦截。npm 审计会联网，TLS中断属于审计未完成，需重试不能当成零漏洞。
2. scripts/test-frontend-smoke.ps1：上一项结束后独立运行11个页面冒烟，检查路由渲染、未知Element组件、浏览器JS错误。
3. scripts/service-status.ps1 和 scripts/backup-status.ps1 -Verify：完成运行检查及备份文件实际完整性核对。
4. scripts/test-database-isolated-restore.ps1：备份只读恢复预检。真正 -Apply 会在**隔离数据库**落盘，不能默认执行，也不能用作原库恢复操作。

本项目内有写入型真实全流程验收脚本 scripts/test-business-flow-real-db.mjs。默认**只复查现有专用验证记录**。没有用户明确授权和限定数据范围，不启用 DPM_FLOW_E2E_ALLOW_WRITE=YES。

## 5. 交付阻塞与已接受边界

**阻塞公开部署**：未开发登录鉴权与权限、未有网络准入审计，不能当作对公众开放的软件服务。Browser Runner 不是OS级系统沙箱，不能访问不可信站点。

**用户暂缓**：Docker、Python/Java脚本 Runner、权限系统、历史22条状态修复、无人工介入的 ChatGPT 后台领取。

**历史数据处理**：目前47轮次相关状态巡检曾有22条“进行中但用例均已结束”告警；继续只读诊断，待逐条核对后另做人工批准的治理计划。

**Git同步**：已积累大量未提交本地代码。只有用户明确要求时才检查并提交/推送；交付时要先清理历史未完成改动、代码审查、建立可回滚tag与部署记录，避免一次提交不可审计的大批次。

## 6. 一次版本开发的交付清单

确认版本需求、最新详细设计、需求覆盖用例、轮次环境+代码版本、每条用例最终结果和附件、失败复核及其后续复测、报告HTML/CSV归档、当日备份有效性、服务守护和运行日志。缺少关键项时应标记“待验证”，不应将创建了轮次等同于完成测试。

这是实际使用的验收清单；不是自动修复工具。脚本和权限的任何变更都要在 T14s 的隔离环境重新验证。
