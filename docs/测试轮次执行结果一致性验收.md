# 第二十一批：测试轮次、执行任务与报告统计一致性验收

## 结论与修复

- 原问题：新执行任务创建时，普通状态更新使用 COALESCE(result, latest_result)，导致本用例在重新执行的 PENDING 阶段，仍保留旧的 PASS/FAIL/BLOCKED/SKIPPED，轮次与报告可能把上一次成功误认为本次成功。
- 新增 ExecutionTaskMapper.resetCycleCaseForNewExecution(cycleCaseId)；只在全新任务 createExecution 路径执行，将 execution_status 设置为 PENDING、latest_result 设置为 NOT_RUN。旧的执行记录始终保存在 dpm_test_execution 中，不会覆盖历史。
- 如果重置失败，抛出冲突异常，由外层有事务的任务创建操作回滚，避免只写入执行任务却未同步用例状态。普通开始、等待人工、恢复和取消继续使用原状态更新；新任务完成时写入新的结果。
- 不改变任何历史业务记录，无需新 DDL。

## 只读全轮次结果校验

执行命令：node scripts/audit-cycle-results.mjs

- 仅允许访问本机 http://127.0.0.1:18090，只用 HTTP GET，不执行创建、取消、恢复或更新。
- 分页校验最多 500 轮（可提供数字作为可选上限），并发最多 4 个轮次。
- 核对轮次列表与详情的用例总数、PASS / FAIL / BLOCKED / SKIPPED / NOT_RUN 各类数量。
- 对照报告复核接口返回的用例元数据、状态、结果、执行次数和关联任务 ID，检查差异。
- 严重不一致则退出码 1；状态为 RUNNING 但用例都结束等旧历史状态仅提示警告，不擅自写数据。
- 输出只包含轮次 ID、错误类型及计数，不打印个人信息、源码、原始快照、凭据、日志。
- 已接入 scripts/test-browser-integration.ps1，所以统一回归加 -BrowserIntegration 时会运行。

## 本地数据巡检发现

初次扫描 45 个轮次、73 条轮次用例，跨模块统计硬性错误 0，发现历史状态告警 22 项。典型现象：轮次 30、29、28、25、23 等仍显示 RUNNING，内部用例和执行任务均已 COMPLETED。

这些是历史记录，不在本批自动执行 UPDATE。后续如果需要修正，应先确认是否允许变更以前的开发测试轮次，并做好备份。
