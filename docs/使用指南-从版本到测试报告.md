# 开发管理系统：从创建版本到完成测试的使用指南

> 适用当前 T14s 本地版本（第42批）。浏览器入口：http://127.0.0.1:18090
>
> 目标：不用了解内部 Java、Vue 或 Runner 代码，也能把一个开发需求从计划推进到验证报告。
> 使用前确认电脑的本地服务正在运行；目前只有 HTTP/Node/Browser 三种固定 Runner 和 ChatGPT 人工交接。
> 不包含 Docker、Python/Java 任意脚本执行，也未启用应用登录与角色权限，请勿直接暴露公网。

## 一、先理解几个概念

| 名称 | 在系统中的意思 | 举例 |
|---|---|---|
| 项目 | 一个持续开发的代码项目 | 开发管理系统 |
| 版本 | 一次要交付的改动集合；**一个版本含多个需求** | 2026.11.2 |
| 需求 | 要实现什么、为什么实现、如何验收 | 测试轮次可以对比 |
| 详细设计 | 如何改接口、数据结构和流程；保留修订历史 | 设计 V1、V2 |
| 测试用例 | 可重复验证的一组步骤和预期结果，可关联一个或多个需求 | TC-001 |
| 测试轮次 | 在某一环境、某一个代码版本上执行一组用例的记录 | 本地自测第1轮、test3第2轮 |
| 执行任务 | 真正执行一个用例或整轮测试的工作单 | 人工、固定脚本、ChatGPT |
| 报告 | 汇总一次轮次的执行结果与证据，也能跨轮比较 | 失败1例、修复2例 |

## 二、首次使用：推荐按照以下顺序操作

### 1. 创建项目

进入 **项目管理** → **新增项目**，填写项目编码、名称、主分支等，保存。
如果项目已存在，就无需重复创建。

在项目列表找到目标项目，点击 **查看版本**，系统自动按该项目筛选版本。

### 2. 创建版本

在 **版本管理** → **新增版本**，选择所属项目，输入版本编号、名称、计划日期与状态。
以后同一项目发布新的代码批次，继续添加版本，不必创建新项目。

在版本行点击 **查看需求**，会自动筛选该版本的需求。

### 3. 录入需求及详细设计

在 **需求与详细设计** → **新增需求**，选择版本并填写编号、标题、需求内容、优先级与负责人。

需求内容建议至少包含：需求背景、业务规则、接口/页面变更、验收标准和必要的边界条件。

创建后找到该需求，点击 **设计** → **新增修订**，使用 Markdown 录入数据库、接口、处理流程及异常方案。
修订历史是新增版本，不会悄悄覆盖旧设计。

**第42批新增的快捷操作：**需求行直接点击 **新增用例**，系统进入“测试用例”并自动打开新建表单，选择来源需求和所属版本。即使关联用例显示 **0条**，也可以点击数字进入只显示当前需求关联用例的列表，再点击 **为此需求新增用例**。

### 4. 编写并关联测试用例

从需求行 **新增用例** 进入时，系统自动：
1. 向服务端核实来源需求真实存在；
2. 根据其 versionId 选好版本筛选；
3. 预选来源需求，展示其编号与名称；
4. 保存前验证该需求仍在完整可选清单中，且没有被取消选择。

此模式下不允许无意移除来源需求；如要创建与该需求无关的独立用例，先点击 **返回全部用例**，再使用普通的 **新建测试用例**。

填写用例编号、名称、步骤操作、每步预期结果、整体预期结果；默认执行方式是 **人工执行**，不需要脚本。
如果使用 **固定脚本**，须先在「自动化脚本」模块创建并启用 HTTP/Node/Browser 脚本，然后在用例内选择它。
选择 **ChatGPT 动态执行**，请补充具体的执行指令与验收方式。

点击保存后，应在需求的 **关联用例 N条** 下钻列表中看到新用例。
旧用例修改后产生修订记录；已有轮次的快照不会被编辑直接覆盖。

### 4.1 创建用例后直接加入计划轮次（第43批）

在「测试用例」列表找到刚创建或已有的**启用**用例，点击右侧 **加入轮次**。第46批起系统会在轮次选项加载完成后**直接打开选择向导**，无需再点击一次「选择目标轮次」；如果已在轮次页面切换来源用例，也会显示新来源的向导。关闭向导或仅查看不会写数据库。

- 系统会读取用例的当前修订和真实关联需求所属版本，只显示**同一版本、尚未开始**的计划轮次。
- 如果这个用例关联了多个版本的需求，会显示这些版本各自的计划轮次。选择前核对显示的版本、轮次名称、测试环境。
- **通用用例**（没有关联需求）可以加入不同版本，但不会因此产生需求/设计覆盖快照，页面会明确警告。
- 选好轮次后点击 **加入所选轮次**，确认后系统再次检查轮次还是「计划中」、版本对应、用例还未加入、修订与需求关联未发生变化。成功后自动打开目标轮次详情查看冻结快照。
- 若没有匹配的计划中轮次，使用 **新建轮次并预选用例**，系统预填版本和这条用例；你仍需填写环境和实际代码版本，再亲自点击创建。
- 轮次进入「进行中」后，不能增删用例。需要复测时应新建下一轮次，保留上一轮完整证据。遇到网络超时，不要重复点击加入按钮；先刷新轮次检查是否已经加入。

### 5. 准备环境并创建测试轮次

首次需要到 **测试环境** 配置环境；普通本地验证优先用本机 TEST 环境，勿误选生产环境。

在版本行点击 **测试轮次** → **新建测试轮次**。
选择当前版本、环境和本轮执行的测试用例，并填写轮次名称、代码版本、阶段等。
保存时会冻结本轮用例、需求及详细设计的快照。注意：
- 一个版本可以有多个轮次，例如本地自测、测试环境第一轮、第二轮复测。
- 不同轮次应明确记录实际环境和**真实代码版本**，才能解释回归差异。
- 更改测试用例或详细设计后，要创建新轮次/新快照，不能默认旧快照随之变化。
- 如果选项加载失败或没显示全部用例，使用页面的“重试加载选项”；不要以不完整候选创建轮次。

### 6. 开始轮次、执行用例并登记结果

打开测试轮次，确认用例清单后点击 **开始**。
根据用例选择 **单用例执行任务** 或 **整轮执行任务**。
系统会留存任务、执行尝试、状态和证据。

- **人工执行**：从执行任务详情开始，按用例步骤操作并登记 PASS/FAIL/BLOCKED/SKIPPED 与观察结果。不要仅凭页面显示按钮就假定测试已运行。
- **固定脚本**：HTTP/Node/Browser Runner 按已有任务领取规则执行。Runner不在线时应先排查服务，不要反复创建新任务。
- **ChatGPT 动态执行**：进入 **ChatGPT 执行台**，复制任务指令并在具备本地工具连接的会话中检查、执行、回写结果。它是**人工交接**，不是自动无人值守的 AI 机器人。
- **人工介入和恢复**：收到暂停/恢复要求时，先打开任务详情核对最新状态与 attempt，再进行确认；网络超时后不要盲目重复 POST。
- **证据附件**：从执行任务的对应 attempt 上传，大小、类型、SHA-256 与归属会被检查。上传成功但客户端丢失响应时，系统先只读核对，未确认前不自动重发。

### 6.1 查看本轮冻结需求覆盖汇总（第44批）

打开 **测试轮次 → 详情**，在轮次环境/代码版本信息下方查看“本轮需求覆盖汇总（冻结快照）”。

- **覆盖需求数**按不同 requirementId 计算；即使多条用例覆盖一个需求，也只计1个需求。
- **通用无需求用例数**独立列示，不能把测试用例数误当成已覆盖需求数。
- 表格按每个需求展示：关联用例数、通过、失败/阻塞、未测，以及有多少关联**缺少本轮冻结时的设计修订快照**。该提示不能代表当前实时需求已删除设计。
- 本页只汇总加入轮次时保存的快照，不会读取后来修改的需求/设计；如果无法核对快照完整性，会显示错误而不是虚构覆盖数。它也不表示版本中“所有需求”都已测试。

### 7. 查看报告与开始下一轮复测

打开 **测试报告**，按轮次名称或代码版本搜索，点击：
- **结果复核**：优先查看失败/阻塞/未执行的用例，必要时点击 **查看执行** 到对应任务。
- **查看报告 / 下载 HTML / 下载 CSV**：复盘结果、保存外部证据；CSV 会对常见敏感赋值和公式注入做防护。
- **轮次对比**：同版本内，取当前轮次以前最近一个状态为**已完成**的轮次，按原始用例 ID 对比 FAIL/BLOCKED→PASS、PASS→FAIL/BLOCKED、持续失败/持续通过，以及本轮新增/移出的用例。

“失败转通过”只表示两轮观察结果不同；是否真正修复根因，仍应结合环境、代码版本和执行证据判断。第44批在轮次对比中直接显示两轮环境、代码版本/Git Commit是否一致；环境或代码不同、或者缺少可比元数据时会提示，不能无条件归因于代码。
首次已完成轮次若没有更早的已完成轮次，会提示无对比基准，不能据此推断改进情况。

## 三、常见问题及处理

| 情况 | 应该怎么做 |
|---|---|
| 需求列表显示关联用例0条 | 可以直接点击 **新增用例**；或点击0条进入需求筛选列表，再从顶部新建 |
| 新建用例提示“来源需求预填失败” | 点击 **重试读取关联需求**。若来源不存在或不在可选清单，返回需求页检查，系统会阻止保存不正确关联 |
| 用例编辑时看不到某个需求/脚本 | 先检查版本筛选、脚本是否启用；若候选请求失败，使用页面重试入口，**不要强行保存不完整关联** |
| 点击“开始测试”没有自动执行 | 创建轮次不等于自动开始，创建任务不等于 Runner 已成功领取；检查轮次状态、任务状态及 Runner 在线情况 |
| 任务已完成却提示恢复失败 | 任务可能已被其他操作完成，先刷新详情；已完成的 attempt 不允许重复恢复/覆盖结果 |
| 上传证据失败或页面响应丢失 | 先查看该执行尝试附件是否已存在；不要连续重发同一个 POST |
| 测试轮次显示 RUNNING 但内部用例已结束 | 到“轮次状态诊断”只读查看；历史存在22个状态偏差候选，**不要自行批量改状态** |
| 想比较本地轮与 test3 轮 | 确认属于同一版本；按“轮次对比”查看结果变化，同时核对两轮环境与代码版本是否一致/可比 |
| 首页统计显示 — | 表示接口数据未成功读取，不表示数量是0；检查后端服务与API健康后刷新 |
| Windows 弹出 CMD/PS 窗口 | 提供发生的准确时间以便查进程来源；当前 Watchdog/Backup 使用无窗口的 wscript 调度 |

## 四、本地服务与备份

项目根目录：`D:\code\dev-process-manager`。默认唯一入口 `http://127.0.0.1:18090`。

- 启动/停止依据已有 `scripts/start.ps1`、`scripts/stop.ps1`；动服务前先只读检查有无 RUNNING 执行任务，避免中断正在执行的测试。
- 服务巡检：`scripts/service-status.ps1`，确认 Spring Boot 与 HTTP/Node/Browser Runner 各只有一个实例、health=UP；watchdog 应显示 WINDOWLESS_LAUNCH=True。
- 备份巡检：`scripts/backup-status.ps1`。自动备份包含 MySQL 与上传附件，备份文件需做完整性校验；**不要把 SQL 直接还原到正在使用的业务库**。
- 隔离恢复验证参考 `docs/数据库隔离还原验收.md`，使用独立目标 MySQL 实例而不是覆盖原实例。
- 发生网络故障、Runner 离线或接口超时，优先检查现有任务详情、执行尝试和事件；业务写请求失败后**不能假定服务端未提交**。

## 五、当前版本的明确边界

1. 不提供应用内登录/权限校验（用户决定暂不需要）；因此只推荐当前受控本机，不暴露公网。
2. 不开发 Docker、Python/Java 任意脚本 Runner；现有 Browser Runner **不等于操作系统级沙箱**，不用于访问不可信站点。
3. ChatGPT 可参与执行任务，但当前执行台是交接入口，**不会在你不操作时自动领取整个队列**。
4. 历史22条异常轮次保留并提供只读诊断，不在正常使用中自动批量修复。
5. 本地改动未按批次自动 Git commit/push；需要同步仓库时由用户明确提出。

## 六、一次验收应具备哪些交付物

在每个版本结束时，建议检查：版本与需求清单、需求的最新详细设计、覆盖需求的测试用例、轮次/环境/代码版本、每条用例的最终结果、需要人工处理的异常任务、失败证据、最终报告及复测对比。做到这些，版本开发过程才真正可追踪。
